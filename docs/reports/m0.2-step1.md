## 2. Assumptions of a 9×12 board, a tile pixel size, or a path that exits off the board

**Sim**

- `level.ts:23-24` `WIDTH = 9`, `HEIGHT = 12`. This is the only place in the sim
  that hardcodes the board size.
- `level.ts:34-43` `PATH` starts at `{x:1, y:-1}` and ends at `{x:7, y:12}`,
  both off-board. Enemies spawn off-board at `posAt(path, 0)` (`tick.ts:282`)
  and leak after walking off the bottom (`tick.ts:400`, see Q6).
- `fixed.ts:10` `TILE = FP_SCALE`. One tile is 1000 world units. Everything
  below is relative to this, which is correct and stays.

**Web**

- `web/game/renderer.ts:183-195` derives pixels-per-tile from
  `terrain.width/height`. **Not** hardcoded.
- `web/components/GameView.tsx:61-64` uses the same derivation for tap targets.
  Not hardcoded. `MIN_TARGET_PX = 44` (`:23`) is a floor, not a board size.
- `web/game/renderer.ts:62-77` glyph and plate sizes are fractions of `TILE`.
  The comment justifies them by the 9-wide board on a phone (the 28px floor).
  Wider maps would shrink glyphs below that floor, with nothing to warn
  about it.
- `web/game/renderer.ts:435-455` `drawWaveSweep` **assumes the lane enters off
  the top edge**: it tints `y = -TILE` and sweeps a head down
  `terrain.height + 2` rows. On a map with an on-board `S`, or any other
  entry side, it sweeps the wrong way.
- `web/components/WavePanel.tsx:24-31` `entryGlyph` **assumes an off-board
  entry**, deriving ⬇/⬆/➡/⬅ from which edge the first waypoint is beyond.
  With `S` on the board it falls through to `⬅`.
- `web/components/WavePanel.tsx:21,37` and `web/game/useGame.ts:18,224,439`
  **import `M0_LEVEL` directly**, so the app can play only one level. Step 4
  replaces this with stage loading.

**Tests**

- `tests/coverage.test.ts:20-35` walks the waypoints and drops cells with
  `y < 0 || y >= height`, which assumes the off-board ends.

## 3. Range units

All ranges are **fixed-point world units, TILE = 1000**. Arrow's 2700 is 2.7
tiles (`towers.ts:105`); the comment at `towers.ts:93` says so.

- `inRange` circle (`tick.ts:493`): `dist2(tower, enemy) <= range²`, in world
  units. Consistent.
- `inRange` lane (`tick.ts:491-492`): `|enemy.dist - tower.laneDist| <= range`.
  That is distance **along the lane**, a different metric in the same units.
- Renderer (`renderer.ts:252`): always draws a **circle** of
  `rangeAtTier(spec.range)` in world units.

**Inconsistency.** The renderer draws a circle for Lance, but the sim uses a
window along the lane. It also draws a 900-radius circle for melee, which the
sim never reads: a blocker engages through `laneDist` crossing
(`tick.ts:362`), not through range. Step 3's "all range is circle range"
removes both mismatches.

## 4. `rangeShape: "lane"`

Exactly one tower: **Lance**, `towers.ts:125`. `ShotEffect.rangeShape` is
declared at `towers.ts:31` and read only at `tick.ts:530`.

**Dropping it is safe.** Lance's 2900 changes meaning from "2.9 tiles along the
lane" to "a 2.9-tile radius". On a spiral that reaches across adjacent lane
runs, so coverage rises; on a long straight run it shortens. That is a balance
change, not a correctness one, and Lance is not in `GOLDEN_ROSTER`
(`["arrow","mortar","frost","venom","hex"]`).

One related field must **stay**. Pierce's hop (`hopMode: "lane"`,
`tick.ts:544,619-622`) picks the next target by `enemy.dist`, the enemy's own
progress along the lane. That is targeting, not range, and does not touch
`Tower.laneDist`. After step 3, `Tower.laneDist` has no readers and can be
deleted.

## 5. RNG draw sites and their order

One sfc32 stream per run, seeded once from `level.seed` (`tick.ts:56`). There
are exactly three draw sites, all inside the input phase:

1. **Summon, type**: `summon.ts:76`, `nextInt(rng, 0, roster.length)`. Only
   after the mana check (`:72`). An unaffordable summon draws nothing.
2. **Summon, tile**: `summon.ts:89`, `nextInt(rng, 0, legal.length)`. Skipped
   on `no_room` (`:82-86`), which refunds and draws nothing more.
3. **Merge, re-roll**: `merge.ts:36`, only after all validity checks
   (`:22-34`). An invalid merge draws nothing.

Across a tick, draws happen in input-array order (`tick.ts:145`). Nothing
outside `applyInputs` draws.

**Is summon tile selection deterministic? Yes.** `legalTileIndices`
(`summon.ts:25-33`) iterates `terrain.tiles` by index, and that array's order
is authored (`level.ts:75-82`: melee tiles first, then platforms). **This
order is part of the replay contract.** `compileMap` must emit slots in one
documented canonical order (proposed: row-major, `y` then `x`), and the
compiler test should pin it.

Summon and merge sharing one stream, so that a merge shifts every later
summon, is already logged as an open item in `docs/README.md`.

## 6. Leak detection

`tick.ts:399-404`: `e.dist = to; if (e.dist >= path.total) { leak }`. **Yes, it
reads `path.total`**, built by `buildPath` (`pathing.ts:28-40`) from the
terrain waypoints. Today `total` includes the off-board stretch to `y = 12`.
With a compiled map, the last waypoint is the centre of `C`, so "reaches `C`"
and "`dist >= total`" are the same test. No logic change is needed, only the
waypoints.

## 8. Does the autoplay bot depend on blocking or melee heuristics?

**The bot has no blocking or melee heuristic.** Its policy (`autoplay.ts:96-151`)
merges by `mergePartners`, optionally only when no legal tile of the tower's
own class is free (`:104-108`, which reads `tileClass`). It summons on mana
and sells the lowest tier when full. `bestUpgrade` (`:161-174`) uses
`hasDamageAxis`, which counts melee attack damage.

**The test rosters and assertions are about melee**: `NO_MELEE`, `AB_NO_MELEE`,
`AB_WITH_MELEE` (`:213-224`), the melee suite in `balance.test.ts:110-129`,
and the `GOLDEN_ROSTER` rationale (`:231-240`), which is all-platform
precisely because blockers die.

## Findings beyond the questions

### F1. `MIN_UNIT_REACH` read from today's data makes every slot dead

The smallest tier-1 range in `TOWER_POOL` is **900** (bulwark, warden, thorn,
`towers.ts:143,153,163`). A slot orthogonally adjacent to the lane is 1000 from
the lane's centreline, so validator rule 6, reading reach from tower data as
specified, would reject **every** slot on every map. The prompt's "reach 1"
assumes the reworked melee has range ≥ 1000. Step 2 builds the validator
before step 3 reworks melee, so either melee's range is set ≥ 1000 as part of
step 3's cleave rework, or rule 6 is tested in step 2 against an injected
reach. I propose the second: `validateMap(terrain, rules)` takes its
thresholds as an argument, and the data default is wired once the melee
numbers exist.

### F2. Fixing `map-spiral-01`

Read as `(x, y)` with `S` at `(0,0)`, the lane runs right along row 0, down
column 5, left along row 5, up column 0 to `(0,2)`, then right to `C` at
`(2,2)`: 21 tiles. Rule 3 passes. At reach 1000, only `(3,3)` has no lane
tile within reach; its four neighbours are slots and `C` at `(2,2)` is
diagonal (1414). **Proposed fix: make `(3,3)` empty**, so row 3 reads
`=##.#=`. That leaves 14 slots, the same count as today's 14 platforms. I'll
confirm this against the real validator in step 2.

### F3. Rigor gaps worth closing while building the scaffolding

These are not in the prompt. Each matters because changes will arrive often
and from someone outside the code.

1. **No CI.** `.github/workflows` does not exist, so the gates run only when
   someone remembers to. A GitHub Actions workflow running test, typecheck,
   lint and build on every push and PR is the single biggest rigor win. It is
   a service, so per `CLAUDE.md` it needs your yes.
2. **Floating point in the sim economy.** `MANA_ACTION_DENSITY = 1.4`
   (`economy.ts:85`), `EXPECTED_KILL_RATE = 0.9` (`:148`),
   `FAMILY_UPGRADE_COST_GROWTH = 1.6` (`:246`), and `Math.round` over float
   products (`:112-115`, `:188-190`, `:251`). IEEE-754 `+ - * /` is
   reproducible across engines, so this is not a live determinism bug, but it
   breaks the "fixed-point wherever an integer works" invariant. Integer
   percentages are a drop-in fix that keeps every value. The new shop's ×1.6
   should be written that way from the start.
3. **Tuning numbers inside logic.** `POISON_INTERVAL`, `MAX_SLOW_PCT` and
   `HOP_RADIUS` (`tick.ts:46-50`) are tuning numbers in the tick file. Move
   them to a constants module so a tuning pass never edits `tick.ts`.
4. **The golden hash does not cover the level.** `hashState` drops `level`
   (`autoplay.ts:196`), so the fixture pins inputs and outcome but not the
   terrain or waves it ran on. The map-hash axis from `CLAUDE.md` closes this;
   step 4 should also assert it inside the golden test.
5. **Stale section references.** About 20 code comments cite "CLAUDE.md §3",
   "§6" or "§8", which no longer exist. Fix them in the commits that touch
   each file anyway (steps 2–3).
6. **Cloud sessions start without `node_modules`.** A SessionStart hook that
   runs `pnpm install` would make every session gate-ready from the first
   command. It is optional and local to `.claude/`.

## Proposed split: scaffolding vs design

The owner's direction (2026-10-12) is that much of the design will come from
Stephanie. That makes M0.2's job building seams that absorb design changes as
data. Read that way, the prompt divides into:

**Scaffolding (no design opinion, build as specified):**
map format, compiler, validator and metrics with thresholds in `mapRules.ts`;
stage registry; run-from-stage; the three version axes and loud guards; wave
scripts referenced by id; generator v0 and its sweep; theme manifest with
fallback; board size derived from the map; extensibility test 6; the
determinism and boundaries gates.

**Design (the prompt's opinion, which Stephanie may revisit):**
removing blocking; melee as cleave and its numbers; one tile class;
circle-only range; the three-button shop and its numbers; deleting patch D;
re-timing the wave script; the `cats` theme's look.

The design half can be built so that it is cheap to change. The shop's
buttons, costs, growth and caps become a data table. Melee becomes an effect
kind with its numbers in data. Tile kinds and their semantics become a table
the compiler reads. If Stephanie later wants blocking back, it returns as an
effect kind plus a tile kind, not as a rewrite.
