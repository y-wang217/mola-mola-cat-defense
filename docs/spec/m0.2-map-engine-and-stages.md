## Design

### Tile kinds (sim semantics)

| char | kind | buildable | lane |
|---|---|---|---|
| `S` | spawn | no | yes, path start |
| `C` | core | no | yes, path end |
| `=` | lane | no | yes |
| `#` | slot | yes | no |
| `.` | empty | no | no |

Tile kinds are data. Each carries its semantics only. How a kind looks is the renderer's business (see Theme).

### Map format

A map is an ASCII grid plus an id:

```
S=====
#####=
==C##=
=####=
=####=
======
```

This is `map-spiral-01`, the shipping map. The lane enters at top-left, runs clockwise and hooks inward to a core inside the spiral. As drawn, slot (3,3) has no lane within reach 1. The validator must catch exactly this. Fix the authored map so it passes, and say in the report how.

### Compiler

`compileMap(ascii) -> Terrain`. Pure.

- Derive the path by walking from `S` through 4-connected lane tiles to `C`, then compress straight runs into axis-aligned waypoints. Waypoints are never authored.
- Output `Terrain` with slots as the only tile class. `TileClass` and `pathDist` on tiles go away.

### Validator (structural gate)

`validateMap(terrain) -> { ok, errors[], metrics }`. A map that fails cannot be loaded into a run, and the error names the rule and the cell. Rules, with thresholds in `mapRules.ts`:

1. Exactly one `S` and one `C`.
2. The lane is a single non-branching 4-connected walk from `S` to `C` that visits every lane tile.
3. **No two non-consecutive lane tiles are 4-adjacent.** Loops must be separated, or the path is ambiguous and visually merges.
4. Lane length within `[LANE_MIN, LANE_MAX]` tiles.
5. Slot count within `[SLOTS_MIN, SLOTS_MAX]`.
6. **No dead slots:** every slot has at least one lane tile within `MIN_UNIT_REACH`, the smallest range any tower has at tier 1. Read it from tower data, not a copy.
7. Board within `BOARD_MAX_W × BOARD_MAX_H`.

Metrics, recorded and not gated: lane length, turn count, slot count, mean lane tiles in reach per slot, mean distinct lane runs in reach per slot (the multi-pass value of a spiral), core depth (lane tiles from spawn to core).

### Reference-style board (sim change)

- Units stand only on slots. Lane tiles are never buildable.
- No blocking. Remove every field from report question 1.
- All range is circle range, in one unit. Drop `rangeShape: "lane"`.
- Melee family becomes short-range circle damage. Starting value: a cleave hitting up to `MELEE_MAX_TARGETS` in range. Melee cannot target fliers, so fliers stay a role check.
- An enemy reaching `C` is a leak. Lives and leak damage are unchanged.
- Summon stays: one button, escalating cost, random roster tower onto a random free slot. No tap-to-place.
- Merge stays unchanged.
- Income model unchanged. `KILL_MANA_SHARE` stays 0.3.

### Shop: three buttons

Replaces patch D. Delete per-tower family upgrades and record the deletion per `CLAUDE.md`.

| button | effect | start cost | escalation | cap |
|---|---|---|---|---|
| Summon | existing summon | existing | existing | none |
| Damage | +`DMG_UPGRADE_PCT` (start 15) to all towers' damage, after tier scaling, at hit time | 50 | ×1.6 | 5 |
| Speed | +`SPD_UPGRADE_PCT` (start 10) to all towers' attack rate | 100 | ×1.6 | 5 |

Inputs `upgrade_damage` and `upgrade_speed` are handled in the existing input phase in the same deterministic order and consume no RNG. Escalation is accumulated in a loop, not `Math.pow`. A refused purchase takes no mana and emits an event.

### Stages

```ts
type MapSource =
  | { kind: "authored"; mapId: string }
  | { kind: "generated"; generatorVersion: number; params: GenParams; seed: number };

type StageDef = {
  id: string;
  map: MapSource;
  waves: string;        // wave script id
  modifiers: string[];
};
```

- `STAGES` is a registry in `packages/sim/src/data/`. A run is created from a `stageId`. `LevelDef` is compiled from the stage, never hand-built.
- `RunSubmission.levelId` becomes `stageId`. Introduce the three version axes from `CLAUDE.md` (`INPUT_LOG_VERSION`, `GENERATOR_VERSION`, map hash) and bump the input log version. A replay whose axis does not match fails loudly, and the message names the axis and both values.
- Wave scripts are referenced by id, so a map and its waves are separable. The current 10-wave script is re-timed for the shorter lane. Stamp lane length next to every benchmark figure, because difficulty is coupled to it. Do not normalize that coupling in this milestone. Add it to the open items in `docs/README.md`.
- `stage-001` = `map-spiral-01` + the re-timed script.

### Generator v0 (`packages/levels`)

`generateMap(params, seed) -> ascii`. Pure, seeded from `sim/rng.ts`, `GENERATOR_VERSION` constant.

- Lane first: a self-avoiding walk from a border spawn, obeying validator rule 3 as it walks, with turn bias and length target from `GenParams`, ending at a core.
- Slots second: every empty cell within reach of the lane, trimmed to the slot range.
- Validate. On a fail, retry with a sub-seed derived from `(seed, attempt)` up to `GEN_MAX_ATTEMPTS`. The attempt index is internal to generation, never player state.
- Shape families such as spiral, serpentine or ring are future generators with the same output type. Build one generator now.

### Theme (render only, `apps/web`)

- A theme manifest maps tile kind plus a 4-bit lane neighbour mask to a texture key and rotation. The lane needs only straight, corner and end, with rotation. Slot, core and spawn are one texture each, plus optional decor for empty tiles.
- Default theme is `cats`. If an atlas fails to load, every tile and unit falls back to coloured rects and glyphs.
- Board layout derives tile size from the stage's map dimensions. No board size is hardcoded.
- Before writing UI code, read `docs/design/design-bible.md`. The step 6 report says which of its rules the UI touched.

## Appendix A: `CLAUDE.md` (commit verbatim in step 0)

```markdown
# CLAUDE.md

Invariants for this repo. A rule is here because it holds for every stage and is
expected to hold for every future one. If a future stage could reasonably
reverse it, it does not belong here.

Current state, milestones, open items and balance numbers are not invariants.
They live in `docs/README.md` and `docs/balance.md`, which change constantly.

Justifications are deliberately absent. Each section points at the document that
carries the argument. If a request conflicts with a rule here, say so instead of
quietly complying.

## The one rule: the simulation is deterministic and pure

`tick(state, inputs) -> state`. Same inputs, same seed, same output,
byte-identical, in the browser and in Node, today and in six months.

Inside `packages/sim`:

- No `Math.random`. All randomness comes from `sim/rng.ts`.
- No wall clock: no `Date.now`, no `performance.now`. Time is the tick counter.
- No pixi.js, React, DOM types, `window` or `document`.
- Fixed 30Hz tick. The sim never sees a frame duration. Render interpolates.
- No iteration over a `Set`, `Map` or object keys where order could differ. Use
  arrays with explicit sort keys.
- Fixed-point integers wherever an integer works (`FP_SCALE = 1000`, helpers in
  `sim/fixed.ts`).
- No draw is keyed or ordered by anything that varies with render, frame rate
  or device.
- Map generation is pure and seeded, and every draw it makes is a function of
  its params, seed and attempt index.

If a change would break determinism, stop and flag it.

Argument: `docs/architecture.md`.

## Architecture

- The dependency arrow points one way: `apps/web -> packages/sim` and
  `packages/levels -> packages/sim`. `packages/sim` imports from neither.
  Asserted by a test, not only by lint, because lint is easy to disable inline.
- Sim state never lives in React state or Zustand. React reads a snapshot per
  frame.
- Every number a tuning pass would touch lives in a named constants or data
  module. If tuning requires editing logic, the split is wrong.
- Content is data: maps, stages, wave scripts, towers, enemies. If adding one
  requires editing logic, the split is wrong.
- A map that fails validation cannot be loaded into a run.
- The server never trusts a client score. It re-simulates the input log and
  compares. Mismatch: reject, log, do not write.
- Never ship future levels to the client.
- Do not add a dependency, a service or a milestone without asking.

Argument: `docs/architecture.md`.

## Versioning

| axis | covers |
|---|---|
| `INPUT_LOG_VERSION` | the input schema |
| `GENERATOR_VERSION` | map generation from params and seed |
| map hash | the compiled terrain a stage resolves to |

- A mismatch fails loudly, and the message names which axis mismatched and both
  values. **Never silently reinterpret a replay or a seed.**
- `INPUT_LOG_VERSION` bumps only when an input kind is added, removed,
  reordered or reshaped.
- Golden replay fixtures change only as an intentional, explained break:
  regenerated in the same commit, with the reason in the message.

## Presentation

The authority on how anything is shown to a player is
`docs/design/design-bible.md`. It is permanent. Stage and patch prompts are
disposable.

- **Where a prompt and the bible disagree on how something is shown, the bible
  wins** until the bible is amended. Where they disagree on what something is,
  the prompt and the data win. The bible governs presentation only.
- The UI presents attributes, never verdicts. No recommendations, no "best"
  markers, no scores or ratings on options, no highlighting or ordering that
  ranks one option above another.
- **No fact that changes a decision is removed. It is re-encoded.**
- The bible changes only through its own amendment process: a disconfirmer
  observed in a playtest, recorded in `docs/design/playtest-log.md`, then a PR
  to the bible.
- If an asset fails to load, the game stays fully playable on fallback
  rendering.

## Process

- Every prompt is committed to `docs/spec/` verbatim **before** work begins on
  it, with a register row. A session must not begin implementation from a
  prompt that is not there. Protocol: `docs/spec/README.md`.
- Where built work deviates from its prompt, do not edit the prompt. Record the
  deviation with a date under its register row.
- Where the register records a decision as made, an instruction in an archived
  prompt to make it again is a record of when it was open, not a live
  instruction.
- **Where a prompt says to report before writing code, that is a hard stop.**
- Commit at each checkpoint and stop for review.
- UI comes last in every stage. If a mechanic cannot be shown to work headless,
  polish does not fix it.
- Sim changes and render changes are separate commits.
- A superseded rule or mechanic is deleted, never left behind a flag, and
  recorded with a dated note in `docs/README.md`.
- A proposed mechanic is run through the design checklist in
  `docs/design/design-notes.md` before it is built.
- Honest assessment over optimistic framing. If an approach is likely to fail,
  say so plainly with the reason.

## Gates and balance

Absolute gates: the determinism suite and golden replays, the boundaries test,
type check, lint, build, and the full suite.

- **Balance is not a gate.** Record the number and keep going.
- Do not retune between checkpoints, and do not move a target to make a miss
  disappear.
- Balance by measurement, never by feel. Instrument first, then tune.
- Benchmark on **mean waves cleared**, not win rate.
- Every benchmark figure is stamped with its seed prefix, seed count, stage id
  and lane length, next to the number. **Read down a prefix, never across.**

Standing policy and the benchmark table: `docs/balance.md` section 0.
```
